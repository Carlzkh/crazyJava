## 2. Bean 是什么

### 2.1 定义

**Bean 就是被 Spring 容器管理的 Java 对象。**

你写的 `UserController`、`UserService`、`UserRepository`，只要加了 `@Controller`、`@Service`、`@Repository`、`@Component` 这些注解，它们就不再是普通的 Java 对象了，而是 **Spring Bean**。

### 2.2 Bean 和普通对象的区别

| 对比项 | 普通 Java 对象 | Spring Bean |
| :--- | :--- | :--- |
| 创建方式 | 你自己 `new` | Spring 容器帮你创建 |
| 生命周期 | 你控制 | Spring 控制（创建、初始化、使用、销毁） |
| 依赖注入 | 手动 `set` 或构造器传入 | Spring 自动注入（`@Autowired`） |
| 代理增强 | 没有 | 可以被 AOP 代理 |
| 获取方式 | 直接引用 | 从容器中 `getBean()` 获取 |

### 2.3 Bean 的作用域（Scope）

| 作用域 | 说明 | 默认 |
| :--- | :--- | :--- |
| singleton | 整个容器只有一个实例 | ✅ 默认 |
| prototype | 每次获取都创建新实例 | |
| request | 每个 HTTP 请求一个实例 | Web 环境 |
| session | 每个 HTTP Session 一个实例 | Web 环境 |
| application | 每个 ServletContext 一个实例 | Web 环境 |

## 3. Bean 的生命周期

### 3.1 核心流程

```
实例化 → 属性注入 → 初始化 → 使用 → 销毁
```

### 3.2 详细阶段

| 阶段 | 做什么 | 示例 |
| :--- | :--- | :--- |
| 1. 实例化 | 调用构造器创建对象 | `new UserService()` |
| 2. 属性注入 | 注入依赖的 Bean | `@Autowired private UserRepository userRepository;` |
| 3. 初始化前 | 调用 `BeanPostProcessor.postProcessBeforeInitialization()` | Spring 内部处理 |
| 4. 初始化 | 调用 `@PostConstruct` 或 `afterPropertiesSet()` | `@PostConstruct public void init() {...}` |
| 5. 初始化后 | 调用 `BeanPostProcessor.postProcessAfterInitialization()` | **AOP 代理就是在这里生成的** |
| 6. 使用 | Bean 可以被调用 | `userService.getUserList()` |
| 7. 销毁 | 容器关闭时调用 `@PreDestroy` 或 `destroy()` | `@PreDestroy public void cleanup() {...}` |

**关键点：AOP 代理是在第 5 步生成的。**

### 3.3 动手验证

在 `UserService` 中加以下代码：

```java
@Slf4j
@Service
public class UserService {

    public UserService() {
        log.info("1. UserService 构造器被调用");
    }

    @PostConstruct
    public void init() {
        log.info("2. UserService @PostConstruct 被调用");
    }

    @PreDestroy
    public void destroy() {
        log.info("3. UserService @PreDestroy 被调用");
    }
}
```

启动项目，控制台输出：

```
1. UserService 构造器被调用
2. UserService @PostConstruct 被调用
```

关闭项目，控制台输出：

```
3. UserService @PreDestroy 被调用
```

### 3.4 依赖注入方式

| 方式 | 写法 | 推荐度 |
| :--- | :--- | :--- |
| 字段注入 | `@Autowired private UserService userService;` | ⚠️ 简单但不推荐 |
| 构造器注入 | `public UserController(UserService userService) {...}` | ✅ 推荐 |
| Setter 注入 | `@Autowired public void setUserService(UserService userService) {...}` | ⚠️ 可选 |

**为什么推荐构造器注入？**
- 依赖不可变（字段可以 `final`）
- 依赖不为空（构造时就必须传入）
- 便于单元测试（不需要 Spring 容器也能 `new`）

## 4. SpringBoot 启动流程

### 4.1 核心入口

```java
SpringApplication.run(CrazyJavaApplication.class, args);
```

### 4.2 五个阶段

```
1. 准备阶段
2. 创建 ApplicationContext
3. 加载 Bean 定义
4. 实例化并初始化 Bean
5. 启动完成
```

### 4.3 详细流程

| 阶段 | 做了什么 |
| :--- | :--- |
| 准备阶段 | 推断应用类型（Servlet / Reactive / None）、加载初始化器和监听器、推断主启动类 |
| 创建 ApplicationContext | Web 应用创建 `AnnotationConfigServletWebServerApplicationContext`，非 Web 创建 `AnnotationConfigApplicationContext` |
| 加载 BeanDefinition | 解析 `@ComponentScan`，扫描 `@Component`、`@Service`、`@Repository`、`@Controller`，加载 `spring.factories` 中的自动配置类 |
| 实例化并初始化 Bean | 反射创建 Bean、注入依赖、执行初始化方法、生成 AOP 代理 |
| 启动完成 | 发布 `ApplicationReadyEvent`，启动内嵌 Tomcat，打印启动日志 |

### 4.4 关键概念：BeanDefinition

`BeanDefinition` 是对 Bean 的**描述**，不是 Bean 本身。它包含：

- Bean 的类名
- 作用域（singleton / prototype）
- 是否懒加载
- 依赖关系
- 初始化方法、销毁方法

**类比：**
- `BeanDefinition` = 房屋图纸
- `Bean` = 实际建好的房子

### 4.5 动手验证：查看容器中所有 Bean

```java
@SpringBootApplication
public class CrazyJavaApplication {
    public static void main(String[] args) {
        ConfigurableApplicationContext context = SpringApplication.run(CrazyJavaApplication.class, args);
        String[] beanNames = context.getBeanDefinitionNames();
        for (String name : beanNames) {
            System.out.println(name);
        }
    }
}
```

启动后你会看到几百个 Bean 名称，其中大部分是 SpringBoot 自动配置注册的基础设施。

### 4.6 Bean 的分类

| 类别 | 示例 |
| :--- | :--- |
| 自己的业务 Bean | `userController`、`userService`、`userRepository`、`userMapper` |
| Spring 核心容器 Bean | `applicationContext`、`environment`、`propertySourcesPlaceholderConfigurer` |
| Web 相关 Bean | `tomcatServletWebServerFactory`、`dispatcherServlet`、`requestMappingHandlerMapping` |
| MyBatis 相关 Bean | `sqlSessionFactory`、`sqlSessionTemplate`、`dataSource` |
| SpringBoot 自动配置 Bean | `dataSourceAutoConfiguration`、`mybatisAutoConfiguration`、`webMvcAutoConfiguration` |
| AOP 相关 Bean | `logAspect`、`annotationAwareAspectJAutoProxyCreator` |

## 5. BeanPostProcessor 与 AOP 代理

### 5.1 定义

> **BeanPostProcessor 是 Spring 的“扩展点”，它允许你在 Bean 初始化前后插入自定义逻辑。**

### 5.2 两个核心方法

```java
public interface BeanPostProcessor {
    // Bean 初始化前调用
    Object postProcessBeforeInitialization(Object bean, String beanName);

    // Bean 初始化后调用
    Object postProcessAfterInitialization(Object bean, String beanName);
}
```

### 5.3 执行时机

```
实例化 → 属性注入 → postProcessBeforeInitialization → 初始化 → postProcessAfterInitialization → Bean 可用
                                                                          ↑
                                                              AOP 代理在这里生成
```

**关键点：AOP 代理是在 `postProcessAfterInitialization` 里生成的。**

### 5.4 为什么 `this` 不是代理对象？

- Spring AOP 的代理对象是**外部**的，它包裹了目标对象。
- 当你调用 `this.getClass()` 或 `this` 时，你拿到的是**目标对象**（`UserController` 本身），而不是外部的代理对象。
- 代理对象拦截了外部的方法调用（比如从 `DispatcherServlet` 进来的请求），并在调用目标方法前后插入切面逻辑。
- 一旦进入目标方法内部，`this` 就回到了目标对象。

**所以 `AopUtils.isAopProxy(this)` 返回 `false` 是正常的，不能用来判断切面是否生效。**

### 5.5 正确的验证方式

**方式一：看日志输出顺序**

AOP 日志在 Controller 日志之前打印，说明切面在方法执行前生效了。

**方式二：用 `applicationContext.getBean()` 拿代理对象**

```java
@Autowired
private ApplicationContext applicationContext;

@GetMapping("/check-proxy")
public String checkProxy() {
        Object bean = applicationContext.getBean("userController");
        return "Bean 类型: " + bean.getClass().getName();
        }
```

访问这个接口，你会看到类似：

```
Bean 类型: com.example.crazyjava.controller.UserController$$EnhancerBySpringCGLIB$$xxxx
```

### 5.6 动手验证：实现自定义 BeanPostProcessor

```java
@Slf4j
@Component
public class MyBeanPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName) {
        if ("userService".equals(beanName) || "userController".equals(beanName)) {
            log.info(">>> [Before] {} 初始化前", beanName);
        }
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        if ("userService".equals(beanName) || "userController".equals(beanName)) {
            log.info(">>> [After] {} 初始化后，实际类型: {}", beanName, bean.getClass().getName());
        }
        return bean;
    }
}
```

启动项目，观察控制台：

```
>>> [Before] userService 初始化前
>>> [After] userService 初始化后，实际类型: com.example.crazyjava.service.UserService$$EnhancerBySpringCGLIB$$d2b16336
>>> [Before] userController 初始化前
>>> [After] userController 初始化后，实际类型: com.example.crazyjava.controller.UserController$$EnhancerBySpringCGLIB$$2c6a9da7
```

### 5.7 验证结论

| Bean | 是否被代理 | 代理原因 |
| :--- | :--- | :--- |
| userService | ✅ 被代理 | `@Transactional`（事务）触发的 AOP |
| userController | ✅ 被代理 | `LogAspect` 切面触发的 AOP |

**验证：把 `UserService` 里所有 `@Transactional` 都注释掉后，`userService` 不再是代理对象。**

## 6. 循环依赖与三级缓存

### 6.1 什么是循环依赖

```java
@Service
public class AService {
    @Autowired
    private BService bService;
}

@Service
public class BService {
    @Autowired
    private AService aService;
}
```

`AService` 依赖 `BService`，`BService` 又依赖 `AService`。这就是循环依赖。

### 6.2 三级缓存

| 缓存 | 名称 | 存储内容 | 说明 |
| :--- | :--- | :--- | :--- |
| 一级缓存 | `singletonObjects` | 完整的 Bean（已初始化） | 最终产物 |
| 二级缓存 | `earlySingletonObjects` | 早期 Bean（未完成属性注入） | 半成品 |
| 三级缓存 | `singletonFactories` | Bean 工厂（ObjectFactory） | 能生成早期 Bean 的工厂 |

**关键：三级缓存放的是工厂，不是 Bean 本身。**

### 6.3 解决流程

```
1. 创建 AService
   → 实例化（new AService()）
   → 把 AService 的工厂放入三级缓存
   → 开始属性注入，发现需要 BService

2. 创建 BService
   → 实例化（new BService()）
   → 把 BService 的工厂放入三级缓存
   → 开始属性注入，发现需要 AService

3. 从三级缓存中获取 AService
   → 调用工厂，生成 AService 的早期引用
   → 把早期引用放入二级缓存
   → 注入给 BService

4. BService 完成初始化，放入一级缓存

5. AService 拿到 BService，完成属性注入和初始化，放入一级缓存
```

### 6.4 为什么需要三级缓存，而不是二级？

**因为 AOP 代理。**

如果 `AService` 被 AOP 代理，那么注入给 `BService` 的应该是**代理对象**，而不是原始对象。

三级缓存里的工厂（`ObjectFactory`）会在调用 `getObject()` 时，判断是否需要生成代理对象：

- 如果需要代理 → 返回代理对象
- 如果不需要 → 返回原始对象

**二级缓存无法做到这一点，因为它只能存对象，不能存“生成对象的逻辑”。**

### 6.5 循环依赖的三种情况

| 情况 | 是否支持 | 说明 |
| :--- | :--- | :--- |
| 单例 + 字段注入 | ✅ 支持 | 三级缓存解决 |
| 单例 + 构造器注入 | ❌ 不支持 | 构造器必须传入依赖，无法提前暴露 |
| Prototype 作用域 | ❌ 不支持 | 每次创建新对象，无法缓存 |

### 6.6 类比：交换变量

| 对比项 | 交换变量 | 循环依赖 |
| :--- | :--- | :--- |
| 中间层存什么 | 临时值 | Bean 的“早期引用”或“工厂” |
| 目的 | 避免值被覆盖 | 避免无限递归创建 |
| 中间层数量 | 1 个（tmp） | 3 个（三级缓存） |
| 是否涉及代理 | 不涉及 | 涉及（AOP 代理对象） |

**核心思想都是：通过中间层打破直接依赖。**

## 7. MyBatis 执行流程

### 7.1 核心问题

**Mapper 接口没有实现类，为什么能执行 SQL？**

**原因：MyBatis 用 JDK 动态代理为 Mapper 接口生成了代理对象。**

### 7.2 完整流程

```
1. 调用 Mapper 接口的方法
   ↓
2. MapperProxy 拦截调用（JDK 动态代理）
   ↓
3. 根据方法名，找到对应的 MappedStatement（即 XML 中 id="findAll" 的 SQL）
   ↓
4. 交给 SqlSession 执行
   ↓
5. 创建 Executor（SimpleExecutor / ReuseExecutor / BatchExecutor）
   ↓
6. 通过 StatementHandler 构建 PreparedStatement
   ↓
7. 通过 ParameterHandler 设置参数
   ↓
8. 执行 SQL，得到 ResultSet
   ↓
9. 通过 ResultSetHandler 映射成 Java 对象
   ↓
10. 返回结果
```

### 7.3 四大核心组件

| 组件 | 作用 |
| :--- | :--- |
| Executor | 执行器，负责调度 |
| StatementHandler | 构建 `PreparedStatement`，执行 SQL |
| ParameterHandler | 设置 SQL 参数 |
| ResultSetHandler | 把 `ResultSet` 映射成 Java 对象 |

### 7.4 MapperProxy.invoke() 源码分析

```java
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        try {
        return Object.class.equals(method.getDeclaringClass())
        ? method.invoke(this, args)
        : this.cachedInvoker(method).invoke(proxy, method, args, this.sqlSession);
        } catch (Throwable var5) {
        throw ExceptionUtil.unwrapThrowable(var5);
        }
        }
```

| 步骤 | 说明 |
| :--- | :--- |
| 判断 `Object` 方法 | 如果是 `toString()`、`hashCode()`、`equals()`，直接执行，不走 SQL |
| `cachedInvoker(method)` | 从缓存中获取 `MapperMethodInvoker`，没有就创建并缓存 |
| `.invoke(...)` | 调用 `MapperMethodInvoker` 的 `invoke` 方法 |
| `this.sqlSession` | 传入当前 SqlSession，用于执行 SQL |

### 7.5 你能用它做什么？

| 场景 | 做法 |
| :--- | :--- |
| SQL 执行慢，想看 SQL | 开启 `mybatis.configuration.log-impl=StdOutImpl` |
| 想知道参数是否传对 | 看日志中的 `Parameters:` 行 |
| 想自定义类型转换 | 实现 `TypeHandler` |
| 想拦截 SQL 做审计 | 实现 MyBatis 的 `Interceptor`（插件） |

## 8. SpringBoot 自动配置原理

### 8.1 自动配置的入口

```java
@SpringBootApplication
```

拆开来看是三个：

```java
@SpringBootConfiguration   // 本质是 @Configuration
@EnableAutoConfiguration   // 核心！开启自动配置
@ComponentScan             // 扫描当前包及子包下的组件
```

**核心是 `@EnableAutoConfiguration`。**

### 8.2 `@EnableAutoConfiguration` 做了什么？

它通过 `@Import(AutoConfigurationImportSelector.class)` 导入了一个选择器。这个选择器会去读取：

```
META-INF/spring.factories
```

这个文件在 `spring-boot-autoconfigure` 这个 jar 包里，里面列了几百个自动配置类。

### 8.3 条件注解：自动配置的“开关”

| 注解 | 含义 |
| :--- | :--- |
| `@ConditionalOnClass` | classpath 下有某个类时才生效 |
| `@ConditionalOnMissingBean` | 容器里没有某个 Bean 时才生效 |
| `@ConditionalOnProperty` | 配置文件中某个属性为特定值时才生效 |
| `@ConditionalOnWebApplication` | 当前是 Web 应用时才生效 |

**这就是为什么：**
- 你引入了 `mybatis-spring-boot-starter`，`MybatisAutoConfiguration` 就生效了
- 你没引入 Redis，`RedisAutoConfiguration` 就不生效
- 你自己定义了一个 `DataSource` Bean，SpringBoot 就不再自动创建默认的

### 8.4 动手验证：查看自动配置报告

在 `application.properties` 中加一行：

```properties
debug=true
```

重启项目，控制台会输出：

- **Positive matches**：生效的自动配置类
- **Negative matches**：未生效的自动配置类

## 9. SpringBoot 常用注解详解

> 本节按注解分类整理成表格，遇到不认识的注解随时回来查。

---

### 9.1 组件声明类注解

| 注解 | 是什么 | 怎么用 | 什么时候用 | 解决什么问题 | 和谁容易混淆 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `@Component` | Spring 最基础的组件注解，标记的类会被扫描并注册为 Bean | `@Component public class MyUtils {}` | 类不属于 Controller/Service/Repository 三种分层时，如工具类、通用处理器 | 让 Spring 管理这个类，可被 `@Autowired` 注入 | `@Service`、`@Repository`、`@Controller` 本质上都是它，只是语义不同 |
| `@Service` | `@Component` 的语义化版本，标注业务逻辑层 | `@Service public class UserService {}` | 写业务逻辑的类，如 `UserService`、`OrderService` | 让代码分层更清晰，功能同 `@Component` | `@Component`，功能没区别，但团队规范要求业务层用它 |
| `@Repository` | `@Component` 的语义化版本，标注数据访问层 | `@Repository public class UserRepository {}` | 封装数据访问逻辑的类，如 `UserRepository` | 语义清晰 + 异常转换（SQLException → DataAccessException） | `@Component`、`@Mapper`，可同时使用 |
| `@Controller` | `@Component` 的语义化版本，标注传统 MVC 控制器 | `@Controller public class PageController {}` | 返回页面的场景（Thymeleaf、JSP） | 让 Spring MVC 识别控制器 | `@RestController`，它返回视图，不是 JSON |
| `@RestController` | `@Controller` + `@ResponseBody` 的组合注解，标注 RESTful API 控制器 | `@RestController @RequestMapping("/users") public class UserController {}` | 前后端分离，接口返回 JSON | 不需要每个方法加 `@ResponseBody`，自动转 JSON | `@Controller`，返回 JSON 用它，返回页面用 `@Controller` |
| `@Configuration` | 声明配置类，替代 XML 配置 | `@Configuration public class CorsConfig {}` | 手动创建第三方对象、统一配置跨域/拦截器/线程池 | 配置逻辑从 XML 搬到 Java，类型安全、可调试 | `@Component`，本质相同，但会被 CGLIB 代理保证 `@Bean` 单例 |
| `@Bean` | 在配置类中手动声明一个 Bean | `@Bean public ObjectMapper objectMapper() { return new ObjectMapper(); }` | 第三方库类无法加 `@Component` 时，如 `ObjectMapper`、`RestTemplate` | 让第三方对象被 Spring 管理，可被注入 | `@Component`，它是类自己声明，`@Bean` 是配置类里手动声明 |

---

### 9.2 依赖注入类注解

| 注解 | 是什么 | 怎么用 | 什么时候用 | 解决什么问题 | 和谁容易混淆 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `@Autowired` | Spring 提供的自动注入注解，按类型注入 | `@Autowired private UserRepository userRepository;` | 需要把别的 Bean 注入当前类时，可放字段、构造器、Setter | 省去手动 `new` 或 `set` | `@Resource`，它按类型，`@Resource` 按名称 |
| `@Qualifier` | 配合 `@Autowired` 使用，指定具体注入哪个 Bean | `@Autowired @Qualifier("mysqlUserRepository") private UserRepository userRepository;` | 同一类型有多个实现时，如 `MysqlUserRepository` 和 `OracleUserRepository` | 解决 `@Autowired` 类型冲突 | `@Resource`，它是配合 `@Autowired` 用，`@Resource` 直接按名称注入 |
| `@Resource` | JDK 自带注解，按名称注入 | `@Resource(name = "mysqlUserRepository") private UserRepository userRepository;` | 想按名称注入时；不想依赖 Spring 的 `@Autowired` 时 | 按名称注入，不需要搭配 `@Qualifier`，默认按字段名找 Bean | `@Autowired`，它按名称，`@Autowired` 按类型 |
| `@Value` | 从配置文件读取单个值注入字段 | `@Value("${api.version}") private String apiVersion;` | 读取 `application.properties` 的配置项，如字符串、数字、布尔值 | 避免硬编码，配置与代码分离 | `@ConfigurationProperties`，它读单个值，后者读一组配置绑定到对象 |

**`@Autowired` vs `@Resource` 对比：**

| 对比项 | @Autowired | @Resource |
| :--- | :--- | :--- |
| 来源 | Spring 提供 | JDK 提供 |
| 注入方式 | 按类型 | 按名称 |
| 需要搭配 | 可搭配 `@Qualifier` | 不需要 |
| 找不到 Bean | 报错 | 报错 |

### 9.5 AOP 类注解

### 10.5 实现 IOC 容器

```java
public class MiniApplicationContext {

    private final Map<Class<?>, Object> beanMap = new HashMap<>();

    public MiniApplicationContext(String basePackage) throws Exception {
        scanAndCreateBeans(basePackage);
        injectDependencies();
    }

    private void scanAndCreateBeans(String basePackage) throws Exception {
        String packagePath = basePackage.replace('.', '/');
        URL resource = Thread.currentThread().getContextClassLoader().getResource(packagePath);
        if (resource == null) {
            System.out.println("未找到包: " + basePackage);
            return;
        }

        File dir = new File(resource.getFile());
        for (File file : Objects.requireNonNull(dir.listFiles())) {
            if (file.getName().endsWith(".class")) {
                String className = basePackage + "." + file.getName().replace(".class", "");
                Class<?> clazz = Class.forName(className);

                if (clazz.isAnnotationPresent(MyComponent.class)
                        || clazz.isAnnotationPresent(MyService.class)) {
                    Object instance = clazz.getDeclaredConstructor().newInstance();
                    beanMap.put(clazz, instance);
                    System.out.println("创建 Bean: " + clazz.getSimpleName());
                }
            }
        }
    }

    private void injectDependencies() throws IllegalAccessException {
        for (Object bean : beanMap.values()) {
            Class<?> clazz = bean.getClass();
            for (Field field : clazz.getDeclaredFields()) {
                if (field.isAnnotationPresent(MyAutowired.class)) {
                    Object dependency = beanMap.get(field.getType());
                    if (dependency == null) {
                        throw new RuntimeException("找不到依赖: " + field.getType().getName());
                    }
                    field.setAccessible(true);
                    field.set(bean, dependency);
                    System.out.println("注入: " + clazz.getSimpleName() + "." + field.getName() + " ← " + field.getType().getSimpleName());
                }
            }
        }
    }

    @SuppressWarnings("unchecked")
    public <T> T getBean(Class<T> clazz) {
        return (T) beanMap.get(clazz);
    }
}
```

| 怎么验证？ | 注释掉所有 `@Transactional` 后，`userService` 不再被代理 |

### 11.3 为什么循环依赖需要三级缓存？

| 问题 | 结论 |
| :--- | :--- |
| 三级缓存放什么？ | 三级存工厂，二级存早期引用，一级存完整 Bean |
| 为什么需要三级而不是二级？ | 因为要支持 AOP 代理，工厂可以动态决定返回原始对象还是代理对象 |
| 构造器注入支持循环依赖吗？ | 不支持 |

### 11.4 为什么 Mapper 接口没有实现类也能执行 SQL？

| 问题 | 结论 |
| :--- | :--- |
| 谁在执行 SQL？ | `MapperProxy` 动态代理 |
| 怎么找到 SQL？ | 根据方法名找到 XML 中对应的 `MappedStatement` |
| 核心组件有哪些？ | Executor、StatementHandler、ParameterHandler、ResultSetHandler |

### 11.5 为什么加个依赖 SpringBoot 就能自动配置？

| 问题 | 结论 |
| :--- | :--- |
| 自动配置的入口是什么？ | `@EnableAutoConfiguration` |
| 配置类在哪里？ | `META-INF/spring.factories` |
| 怎么判断是否生效？ | `@ConditionalOnXxx` 条件注解 |
| 怎么查看生效情况？ | `debug=true` 查看自动配置报告 |

## 12. 经验总结

1. **Bean 的生命周期**：实例化 → 属性注入 → 初始化 → 使用 → 销毁。AOP 代理在 `postProcessAfterInitialization` 中生成。
2. **`this` 不是代理对象**：在方法内部，`this` 指向目标对象，不能用 `AopUtils.isAopProxy(this)` 判断切面是否生效。
3. **`@Transactional` 会触发代理**：即使没有自定义切面，`@Transactional` 也会让 Bean 被代理。
4. **循环依赖靠三级缓存**：三级存工厂，二级存早期引用，一级存完整 Bean。工厂的存在是为了支持 AOP 代理。
5. **MyBatis 靠动态代理**：Mapper 接口没有实现类，但通过 `MapperProxy` 动态代理，调用方法时找到对应的 SQL 执行。
6. **自动配置靠条件注解**：`@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 决定哪些配置生效。
7. **手写 IOC 容器是最好的巩固**：把 Bean、生命周期、依赖注入全部串起来，真正内化。
